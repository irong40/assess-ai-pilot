<objective>
Implement human approval gates for high-risk agent actions, extend the audit trail with agent-specific fields, enforce multi-tenant data isolation, and establish the CUI-free data architecture with documentation.

Purpose: Completes the trust and safety layer. Without approval gates, agents could take unreviewed actions. Without tenant isolation, one company could see another's data. Without CUI-free documentation, customers cannot trust the platform with compliance data.
Output: agent_approvals table, approval gate logic (server + client), enhanced audit trail, multi-tenant isolation tests, and DATA-HANDLING.md for customers.
</objective>

  <behavior>
    - classifyRisk returns 'high' for destructive actions (delete, modify_policy, override_control)
    - classifyRisk returns 'medium' for analytical actions (gap_analysis, generate_report)
    - classifyRisk returns 'low' for read-only actions (query_control, check_status)
    - isApprovalRequired returns true for 'high' risk, false for 'low' and 'medium'
    - Approval state machine: pending -> approved|rejected; approved -> executed; rejected -> cancelled
    - Expired approvals (past expiry_at) are treated as rejected
    - Only users with role 'admin' or 'issm' can approve high-risk actions
  </behavior>
  <action>
    1. Create `src/lib/__tests__/approval-gate.test.ts` testing all behaviors above. Use a set of known action strings to test risk classification. Test the approval state machine transitions.

    2. Create `src/lib/approval-gate.ts` with client-side helpers:
       - `classifyRisk(agentType: AgentType, action: string): RiskLevel` -- uses a lookup table of action patterns to risk levels. Destructive verbs (delete, modify, override, revoke, disable) map to 'high'. Analytical verbs (analyze, assess, generate, report) map to 'medium'. Read verbs (query, check, list, view) map to 'low'. Default to 'medium' for unknown actions.
       - `isApprovalRequired(riskLevel: RiskLevel): boolean` -- returns true for 'high' only
       - `APPROVAL_ROLES: string[]` = ['admin', 'issm'] -- who can approve

    3. Create `supabase/functions/_shared/approval-gate.ts` with server-side logic:
       - `checkApprovalRequired(task: AgentTask): boolean` -- mirrors client-side isApprovalRequired
       - `createApprovalRequest(supabase, task: AgentTask): Promise<string>`:
         a. Insert row into agent_approvals: task_id, company_id, agent_type, action_description, risk_level, status='pending', requested_at=now(), expiry_at=now()+24h
         b. Call `notify_approval_needed` RPC to broadcast via Realtime to `company:{company_id}` topic
         c. Return approval_id
       - `processApprovalDecision(supabase, approvalId, decision: 'approved'|'rejected', userId)`:
         a. Validate user has admin or issm role
         b. Check approval hasn't expired
         c. Update agent_approvals status, set decided_by, decided_at
         d. If approved: update linked agent_task status to 'approved'
         e. If rejected: update linked agent_task status to 'rejected'
         f. Log decision to audit_log with approver's reasoning

    4. Create `supabase/migrations/YYYYMMDD_approval_gates.sql`:
       - Create `approval_status` enum: pending, approved, rejected, expired, executed, cancelled
       - Create `agent_approvals` table: id (UUID PK), task_id (UUID NOT NULL REFERENCES agent_tasks(id)), company_id (UUID NOT NULL REFERENCES companies(id)), agent_type (agent_type NOT NULL), action_description (text NOT NULL), risk_level (risk_level NOT NULL), status (approval_status NOT NULL DEFAULT 'pending'), requested_at (timestamptz DEFAULT now()), expiry_at (timestamptz DEFAULT now() + interval '24 hours'), decided_by (UUID REFERENCES profiles(id)), decided_at (timestamptz), decision_reason (text), created_at (timestamptz DEFAULT now())
       - Enable RLS: SELECT/UPDATE for authenticated users WHERE company_id matches profile AND user role in ('admin', 'issm') for UPDATE
       - Index on (company_id, status), index on task_id
       - Create `notify_approval_needed` function (from research Pattern 4) that calls `realtime.send()` to broadcast to `company:{company_id}` topic

    5. Create `supabase/migrations/YYYYMMDD_audit_agent_fields.sql`:
       - ALTER TABLE audit_log ADD COLUMN agent_id UUID REFERENCES agent_tasks(id)
       - ALTER TABLE audit_log ADD COLUMN agent_type agent_type
       - ALTER TABLE audit_log ADD COLUMN reasoning_summary text
       - These fields are nullable (existing non-agent audit entries remain valid)
       - Update log_audit_event RPC to accept new optional parameters: p_agent_id, p_agent_type, p_reasoning_summary

    6. Update `supabase/functions/_shared/agent-base.ts` (from Plan 02) to integrate approval gates:
       - Import `checkApprovalRequired, createApprovalRequest` from `./approval-gate.ts`
       - In executeAgentTask, after handler returns successfully:
         - If checkApprovalRequired(task) is true: call createApprovalRequest, set task status to 'awaiting_approval', return early (output is held until approved)
         - If false: proceed to set status 'completed' and write output as before
       - When calling log_audit_event, pass the new agent_id and agent_type parameters
  </action>

    - audit_log extended with agent_id, agent_type, reasoning_summary columns
    - Server-side approval-gate.ts creates requests and broadcasts via Realtime
    - agent-base.ts integrates approval check into executeAgentTask flow
